Scoring scope

An excluded status is out of scope everywhere at once: not scored, not counted in the calendar, the day list, the leaderboard or the Slack report, and not billed. Deterministic R-checks still run at fetch time, and the tickets are still fetched and stored, so an exclusion is reversible.

Shown here for context. Statuses are chosen in Admin → Ticket statuses, which lists every status Pylon has actually sent with the number of tickets in each, so you can see what excluding one costs before you do it. Keeping one editor means the two cannot disagree.

Required conditions

A ticket escalated to oncall passes R8 only when every ticked condition holds. Untick one to stop requiring it — that is how to drop a field Pylon still defines but nobody fills any more, without switching the whole check off. All four unticked is refused: an R8 with no conditions passes every oncall ticket, which looks like a working check and is not one.

Workspace-specific guidance

Appended to the rubric on every run, after the sections below. Changing this can shift grades: each run records whether guidance was active. Max 4000 characters.

The grading prompt, section by section

This is the grading policy itself — what “Good” means, how strict A5 is, how ties are broken. It used to be a string literal in the scorer, which made policy a deploy. Editing a section here is a normal, audited rules change. An empty box is valid and falls back to the shipped default.

Editing these changes what “Pass” means. The assembled prompt is hashed into every ticket's fingerprint, so a save marks existing grades stale: re-running a date will regrade it rather than skip it. Nothing is re-billed until someone deliberately re-runs a specific date — a save on its own costs nothing and rewrites no grade.
Show the fixed blocks (not editable — the wire contract, not policy)
These describe the mechanism: how results are correlated back to tickets and what JSON shape must come back. Editing them would not change a grade, it would break scoring, so they stay in code.

Prompt dry-run

Grades a handful of already-scored tickets with the draft text in the boxes above — the guidance and every rubric section as currently typed — and shows what would move. A dry-run saves nothing and writes no grades: no ticket's stored verdict changes and no run is recorded. To keep an edit, press Validate & save.

This spends money. A dry-run makes real AI calls — five tickets sent to the model, billed like any other scoring. The figure reported afterwards is an estimate, not a metered charge.

Ticket statuses

What each Pylon status means to the checks. This replaced five overlapping lists in code, seeded to match them exactly — so nothing moved when it was adopted, and a status Pylon adds later arrives as a row to decide about rather than silently defaulting.

In scope — scored and counted at all. Reply owed — whether R4's clock runs, or the status short-circuits to Pass. R5 expects — who owns the next action, and what proves it. Engineering — whether R7 applies. These are independent: a closed ticket owes no reply but is still graded, because A5 exists to judge closures.

Pylon fields

Which Pylon custom field each check reads. These were fixed in code, so following a field Pylon renamed or retired meant a deploy — and until that deploy the check fails every ticket, because a field that is not there reads the same as one left blank.

Learned suggestions

Every reviewer sign-off that disagrees with the AI is a labelled example of the grading being wrong. Grouped by the check that produced the verdict, a pattern becomes a proposal to edit one specific rule. Nothing here is applied. The system proposes and shows its evidence; a person reads it, decides, and makes the change through Validate & save like any other rule edit — so there is always someone who can say when the meaning of “Pass” changed, and why.
